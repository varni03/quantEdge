# Deferred — v2 and beyond

**This file is the pressure valve.** The single biggest risk to quantEdge is scope creep
across four feature pillars producing a half-built everything. When a good idea arrives
mid-phase, it gets written down here instead of built. Nothing leaves this file until the
current phase's "done when" gate has passed.

---

## Deferred on compliance grounds

**Risk-tolerance onboarding that generates a starter portfolio.** Producing a personalized
allocation from a user's stated risk tolerance is close to the textbook definition of
investment advice, and quantEdge's whole compliance position is that it provides analytics and
education rather than recommendations.

The v2 version is reframed as *educational comparison*, not assignment: "here is what a
classic 60/40 allocation has historically looked like", "here is how a diversified portfolio
behaved in 2008 versus a concentrated one". Explore model allocations; never assign one to a
specific person.

**Tax-loss harvesting suggestions.** Same reasoning — identifying losses is analysis, but
recommending which lots to sell for tax purposes is advice, and tax advice specifically. The
lot engine already tracks `holdingPeriodDays` and `isLongTerm`, so the *data* is there; what's
deferred is anything phrased as a suggestion.

## Deferred on cost/complexity grounds

**A Python quant service.** Not needed for anything in v1 — every metric in scope is an O(n)
pass over an array, and a 10,000-path Monte Carlo runs in under 100ms in plain V8. It becomes
worth revisiting only for genuinely hard numerics: convex portfolio optimization (`cvxpy`),
proper Fama-French factor regressions (`statsmodels`), vectorized backtesting (`vectorbt`).

The escape hatch is already built and cost nothing: all computed metrics land in
`metrics_snapshots`. A Python batch job can write into the same table and the app never learns
which language produced a number.

**A paid market-data provider.** `yahoo-finance2` is unofficial and will eventually break.
The provider interface plus the ESLint import restriction means replacing it is a one-file
change. Migration path when this becomes a real product: Tiingo (~$10/mo, strong EOD +
fundamentals) → Polygon (~$29/mo, intraday + websockets).

**Real-time / intraday data.** The provider supports it; v1 deliberately uses daily bars only.
Intraday multiplies data volume by ~400× and forces a rethink of the whole bar-cache strategy.

**Multi-currency portfolios.** v1 is US-only by decision. Foreign tickers are recognized but
flagged and excluded from portfolio totals rather than silently summed as if they were dollars.
Full support needs an FX rate series, per-transaction `fxRate` capture (the column already
exists), and cost-basis math that tracks both the local and base currency — which is where
subtle bugs live. Also note the GBp trap: London prices arrive in pence, not pounds.

**Cache Components / `use cache`.** Not enabled, deliberately. On serverless, `use cache`
entries live in an in-memory LRU that doesn't persist across requests, so it wouldn't address
the actual constraint (a third-party rate limit) — the database-backed bar cache does that.
Enabling it also removes the `dynamic`/`revalidate` segment config and adds prerender failure
modes around short cache lifetimes. Revisit purely as a latency optimization once the data
layer has settled.

## Feature ideas

- **Paper trading mode.** `portfolios.is_paper` already exists as a column. Simulate trades
  against real prices without real money.
- **Scenario / stress testing.** "What if 2008 happened to my current portfolio?" Replay a
  historical window's returns against present-day weights.
- **Brokerage sync** via Plaid or SnapTrade. The most magical onboarding possible — holdings
  appear with no typing — but it adds real auth and compliance surface.
- **Options positions.** Needs Greeks, expiry handling, and assignment logic; a different
  quant domain rather than an extension of this one.
- **Factor exposure.** Value/growth/momentum/quality/size tilt versus the benchmark. Wants
  proper regressions, which is the strongest single argument for the Python service.
- **Dividend reinvestment (DRIP) modelling.** Currently dividends are recorded manually as
  transactions; automatic reinvestment at the ex-date price would need care to avoid
  fabricating lots the user never actually owned.
- **Push / SMS alert delivery.** In-app plus email covers v1.
- **Rule backtesting beyond 90 days**, with a summary of hit rate and average forward return —
  approaching a genuine research tool, and worth being careful that it doesn't start reading
  as a recommendation engine.
- **Correlation over multiple windows** (30/90/365 day) to show correlations rising in a
  drawdown, which is exactly when diversification is supposed to help and often doesn't.
- **Portfolio comparison** against a named model allocation, framed educationally.

## Engineering debt to revisit

- **No tests outside `lib/quant` and `lib/portfolio`.** Deliberate: those are pure functions
  where silently-wrong math hides, and a narrow fast suite is what survives. Component and
  E2E tests are worth adding once the UI stops moving.
- **Next.js proxy-bypass advisory** (`GHSA-6gpp-xcg3-4w24`, Middleware/Proxy bypass in App
  Router with Turbopack). No stable fix exists as of Next 16.2.12 — the patch is only in a 16.3
  preview. v1 has no auth middleware, so nothing is exposed. **Gate on this before enabling
  auth:** either upgrade to a patched stable release, or rely on route-handler and RLS
  enforcement rather than `proxy.ts` for authorization. The Next docs independently insist on
  this anyway — "verify authentication and authorization inside each Server Function rather
  than relying on Proxy alone."
- **The eslint dev-toolchain audit warnings** (`brace-expansion` DoS via `minimatch`) are
  dev-only and fixing them requires ESLint 10, a breaking upgrade. Not worth it yet.
- **Yahoo cookie jar on serverless.** The library notes that a database- or Redis-backed
  cookie jar speeds up cold starts, since the initial cookie fetch is the slow part. Worth
  doing if cold-start latency becomes visible.
